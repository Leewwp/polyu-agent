# 03 · Phase 0M：模型选型与评测计划

> 定稿：2026-09-03。本文档定义 PolyU 场景四类模型角色（Embedding / Reranker / 辅助 Chat / 主 Chat-Agent）的候选方案、分层评测方法、决策规则与锁定时机。只记录原则与计划：**不预设胜者，本轮未改动任何模型配置、未调用任何模型、未产生任何费用。**
> 位置：**Phase 0B（最小运行环境 + 测试语料，设计见 [`02-Phase0-ragent底座适配性审计.md`](./02-Phase0-ragent底座适配性审计.md) §7）之后、大规模语料入库（AR / Library / SAO 500–1500 页）之前**，作为路线图上的决策门。
> 编号说明：`02` §6.2 曾预留 `03-Phase0B-垂直切片实施记录.md` 文件名；本文件占用 03 编号后，Phase 0B 实施记录顺延为 `04`（`02` 为历史审计记录，不再修改）。

## 一、决策背景

1. ragent 1.1.0 默认链路（SiliconFlow `Qwen/Qwen3-Embedding-8B` → pgvector 1536 维 → RRF → 百炼 `qwen3-rerank` → chat 路由 standard tier）是底座作者的经验默认值，**从未在 PolyU 英文语料 + 中英混合问法上验证过**。`02` §4.7 已把"中文问题检索英文文档"列为必须实测的未知项（R1），代码侧无任何跨语逻辑，效果完全取决于模型自身多语能力。
2. 模型市场迭代快（qwen3.7 / qwen3.8 系列同期可用），厂商 Benchmark 不代表垂直场景表现。**最终选择必须以 PolyU 真实语料上的可复现评测结果为依据，而不是厂商 Benchmark。**
3. Embedding 一旦锁定并大规模入库，更换意味着全量重建向量库。因此 Embedding 必须**先于**全量入库完成评测与锁定——这是 Phase 0M 作为独立决策门存在的根本原因。
4. Chat 类模型经底座路由机制（`rag.ai.chat.candidates` + tiers，`application.yaml:216-251`）可随时配置切换，无需在 Phase 0 初期永久固定；但每次切换需回归验证引用忠实性与工具调用，防止隐性退化。
5. 模型横向对照、跨语言评测与成本分析将作为项目技术亮点沉淀（§十），可用于 GitHub README、项目总结与个人简历。

## 二、质量优先原则（2026-09-03 定案）

1. **开发与验证阶段以最终效果为第一优先级，成本暂时是次要指标。**
2. 成本仍需完整记录（§八），但不为节省少量费用提前牺牲 Embedding、Reranker 或回答质量。
3. 项目正式部署、用户量增加后，再依据真实调用量、延迟和账单进行降本。
4. 当前所有模型都只是候选方案，**不预先指定最终胜者**；保留对照组与挑战组，通过相同语料、相同分块、相同问题集做可复现评测。

## 五、分层评测方法

总原则：**不做笛卡尔积组合**。逐层推进，每层固定上游胜者；同语料快照、同分块参数（ChunkBudget）、同检索参数（default-top-k 10 / recall-budget 20 / rerank-candidate-limit 40）。每次评测记录：语料 URL 清单与抓取日期、解析器、分块参数、检索参数、模型快照 ID、评测日期——保证可复现。

### 5.1 第一层：Embedding

- 语料：与 Phase 0B 种子清单**同一批 20–50 个 PolyU 英文页面**，解析结果与 Chunk 完全一致。
- 隔离：不同 Embedding 使用**独立知识库或独立 Collection**，绝不混用向量。
- 指标：英文问题与简体中文问题各自的 HitRate@10、MRR；跨语言召回损失（§六）；查询延迟；入库总 Token、费用与时长。
- 独立变量：英文检索 Instruction 前缀（如 API 支持）作为单独变量记录"有/无"对比，不与其他变量混合。
- 产出：胜者**立即锁定**（§九），后续全量入库建立在锁定向量空间上。

### 5.2 第二层：Reranker（固定第一层胜者）

三臂对比：

1. 不使用 Reranker（消融基线）；
2. `qwen3-rerank`；
3. `qwen3.7-text-rerank`。

记录：正确证据进入 Top 3 的比例；MRR / 排序提升（相对臂 1）；P50/P95 延迟；每次请求 Token 和成本。

### 5.3 第三层：Chat/Agent（固定相同检索结果与上下文）

对每个问题固定同一份检索上下文（留存快照），逐主 Chat 候选生成并评分：

| 维度 | 记录内容 |
| --- | --- |
| 答案质量 | 答案正确性、操作步骤完整性 |
| 忠实性 | 引用忠实性、无依据内容与幻觉 |
| 边界 | 不可回答问题的拒答表现 |
| 语言 | 英文与简体中文表达质量 |
| 工具 | Function Calling 参数正确率 |
| 性能 | 首 Token 延迟、总延迟 |
| 成本 | 输入 / 输出 / 思考 Token；单次与每千次问答的估算成本 |

**决策规则**：低成本候选与质量基准的核心质量差距不超过约 5 个百分点 → 优先选低成本候选；若引用忠实性、拒答能力或工具调用可靠性明显下降 → 选质量更高的模型（这三项为一票否决项，不受 5pp 规则保护）。

## 六、评测数据集设计

同一事实设计成对问题：

| 类型 | 数量 | 是否计分 |
| --- | --- | --- |
| 英文问题 | 8 | ✅ |
| 简体中文等价问题（与英文题同一事实成对） | 8 | ✅ |
| 简体中文口语化问题（小红书式） | 2 | ✅ |
| 英文不可回答问题 | 1 | ✅ |
| 简体中文不可回答问题 | 1 | ✅ |
| 繁体中文冒烟问题 | 2–3 | ❌ 不计入主要评分 |

合计 20 条计分题 + 2–3 条冒烟题。每条计分题标注 gold 文档与锚文本（可接受答案集合），使 HitRate@10、MRR、Top 3 证据比例可自动计算；不可回答题明确"语料外"判定口径（检索命中情况 + 人工确认）。

核心指标：**跨语言召回损失 = 英文 HitRate@10 − 简体中文 HitRate@10**。

与 [`01`](./01-项目规划与路线图.md) §六评测集（80–100 条）的关系：本集是模型选型专用小集（每个候选都要跑，控制评测时长与费用），标注规范与其保持一致；Phase 0C 的大评测集复用本集全部 20 题作为种子。

## 七、指标与决策规则汇总

| 层 | 主指标 | 硬门槛 | 平局裁决 |
| --- | --- | --- | --- |
| Embedding | EN/ZH HitRate@10、跨语言召回损失 | 跨语损失不塌方（对照 `02` §7.4 检查点①） | MRR → 查询延迟 → 入库成本 |
| Reranker | Top 3 证据比例、排序提升 | —（臂 1 为消融基线） | 延迟预算内取提升更大者，成本次之 |
| Chat/Agent | 正确性 + 引用忠实性 + 拒答 + FC 参数正确率 | 引用忠实性 / 拒答 / 工具调用不得明显回退 | 5pp 规则 → 延迟 → 每千次成本 |

自动指标（HitRate / MRR / 延迟 / Token）脚本计算；主观维度（正确性、步骤完整性、表达质量）人工评分，全部原始输出留存备查。

## 八、成本记录方法

1. **价格三要素**：所有价格必须标注查询日期、供应商和地域，并说明价格可能变化；免费额度和限时优惠不作为长期架构决策依据。
2. **一次性 vs 持续**：Embedding 入库成本通常是一次性成本——开发期优先选择效果更好的方案；Chat、Reranker、问题改写、多轮历史是持续调用成本，是降本的主战场。
3. **降本优先级**（部署后）：① 减少无效调用（改写开关、多轮历史裁剪）② 控制候选数量（rerank-candidate-limit / topK）③ 控制上下文长度 ④ 控制输出长度——全部排在"换更便宜的模型"之前。
4. **部署前重算**：按预计 DAU × 每人日均问题数 × 实际 Token 统计，重算全链路成本（改写 + 意图 + 检索 + 重排 + 生成）。

## 九、模型锁定与重新评测时机

| 角色 | 锁定策略 | 重新评测触发 |
| --- | --- | --- |
| Embedding | 第一层评测后**立即锁定**，全量入库建立在锁定向量空间上 | 新模型在同一评测集上优势显著；供应商停服 / 涨价不可接受；后续检索评测塌方。解锁代价＝全量重 embedding + 重建向量库，必须先估算 Token 成本与时长再决策 |
| Reranker | 不锁死，配置迭代 | Embedding 更换后必重跑第二层；语料规模跃变 |
| 辅助 Chat | 随主链路配置迭代 | 改写 / 意图 / 摘要等结构化任务质量反馈下降 |
| 主 Chat | 路由与配置迭代，不永久固定；`qwen3.8-max` 只进 deep tier（深度模式 / 兜底） | 每次切换跑本数据集回归小集；上游模型重大版本发布 |

统一重评触发器：语料规模翻倍（20–50 → 500–1500 → 全站）、检索配置大改、上游模型重大版本、线上质量反馈下降。

## 十一、尚未验证的兼容性与风险

| # | 风险 / 未知 | 等级 | 验证方式 |
| --- | --- | --- | --- |
| 1 | `qwen3.7-text-embedding` × ragent 1.1.0 兼容性：底座百炼供应商只配置了 chat（compatible-mode）与 rerank（原生 dashscope）端点（`application.yaml:190-195`），而 embedding 客户端走 OpenAI 兼容 `/v1/embeddings` 且显式 `dimensions=1536`（`02` §4.7）——端点配置、维度参数、返回格式均需实测，可能需在配置层新增候选 | 中 · 未知 | 接入前最小冒烟（1 条文档 + 1 条查询）；失败则该候选出局，或仅在配置层小改（不动核心链路） |
| 2 | `qwen3.7-text-rerank` 与底座 rerank 客户端（原生 dashscope rerank 端点，失败降级 noop）的参数与返回兼容性 | 中 · 未知 | 同上；冒烟通过后进第二层三臂对比 |

| 5 | Function Calling 支持度：主 Chat 候选的 FC 参数正确率未验（底座 MCP 工具链依赖） | 中 | 第三层评测覆盖 FC 维度 |
| 6 | 供应商速率限制与地域网络延迟差异（SiliconFlow vs 百炼） | 低 | 记录测试地域与限流表现；P95 标注含网络因素 |
| 7 | 免费额度 / 限时优惠的不确定性 | 低 | 评测设计为可重放，不依赖一次性额度 |

## 十二、执行清单（过门条件）

1. 前置确认：Phase 0B 出口达成（最小环境可用 + 20–50 条种子页入库 + 引用链路验证，见 `02` §7.4）。
2. 建评测集（§六：20 计分 + 冒烟）与 gold 标注。
3. 第一层 Embedding 横评（含 Instruction 独立变量）→ **锁定并记录**。
4. 第二层 Reranker 三臂对比。
5. 第三层 Chat 横评 + 辅助 Chat 结构化任务冒烟。
6. 汇总成本表（§八）与评测报告（§十产出），更新 `CHANGES.md` 与 `01`。
7. **过门**：进入 Phase 0C 大规模语料入库。
